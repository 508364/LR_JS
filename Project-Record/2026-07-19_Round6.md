## 新增文件

### `src/lr_compress.h` / `src/lr_compress.c`

**纯 C 实现 LZ4 块压缩**：
- 哈希表匹配查找（16-bit 哈希，64KB 窗口）
- 最小匹配长度 4 字节，最大 259 字节
- 解压速度极快（~2-4 GB/s）
- 压缩率：JS 字节码 ~40-60%

**API**：
- `lr_lz4_compress()` - LZ4 块压缩
- `lr_lz4_decompress()` - LZ4 块解压
- `lr_compress_if_beneficial()` - 智能压缩（仅当压缩率 > 阈值时压缩）
- `lr_decompress_if_needed()` - 智能解压

**压缩格式**：
- 原始大小 4 字节头 + LZ4 块数据
- 仅当压缩后节省 > 10% 空间时才使用压缩（`min_ratio = 0.90`）
- 小于 64 字节的数据不压缩

## 修改的文件

### `src/lr_bytecode.h`

- 版本号从 1 升级到 2
- 新增 `LR_BYTECODE_FLAG_COMPRESSED` (1 << 2) 标志位
- `LR_BytecodeCache` 新增字段：
  - `int compression` - 启用/禁用 LZ4 压缩
  - `int64_t bytes_saved` - 压缩节省的字节数
- 新增 API：`lr_bytecode_cache_set_compression()`

### `src/lr_bytecode.c`

- `lr_bytecode_cache_init()`: 默认启用压缩 (`compression = 1`)
- `lr_bytecode_cache_store()`: 压缩存储流程
  - 如果 `compression` 启用且字节码 > 256 字节，调用 `lr_compress_if_beneficial()`
  - 压缩后设置 `LR_BYTECODE_FLAG_COMPRESSED` 标志
- `lr_bytecode_cache_load()`: 解压读取流程
  - 检查 `flags & LR_BYTECODE_FLAG_COMPRESSED`
  - 如果压缩，调用 `lr_decompress_if_needed()` 解压
  - 兼容旧版（version 1）缓存文件
- `lr_bytecode_cache_set_compression()`: 新增
- `lr_bytecode_cache_stats_ctx()`: 统计输出增加压缩状态和节省字节数

### `src/lr_sandbox_log.h`

- `LR_SandboxLog` 新增字段：
  - `LR_SandboxLogLevel current_level` - 当前日志级别（运行时可变）
  - `LR_SandboxLogLevel default_level` - 默认级别
- 新增 API：`lr_sandbox_log_get_level()` - 获取当前日志级别

### `src/lr_sandbox_log.c`

- `lr_sandbox_log_init()`: 初始化 `current_level = LR_SLOG_INFO`
- `lr_sandbox_log_set_level()`: **实际实现**（之前是空函数）
  - 线程安全地设置 `current_level`
- `lr_sandbox_log_get_level()`: 新增，返回当前级别
- `lr_sandbox_log_write()`: 新增级别过滤
  - 如果 `level > current_level`，跳过该日志条目
  - 示例：`current_level = INFO` 时，DEBUG/TRACE 级别被过滤

### `src/lr_runtime.c` - 性能优化

**eval 热路径优化**：
- 移除 `lr_eval()` 中的 `lr_compute_memory_usage()` 调用（两次完整堆扫描）
- 改为简易计数器：`bytes_since_last_gc += source_len`
- 仅在计数器超过阈值时触发 GC 检查
- 减少每次 eval 后的内存扫描开销

**eval_file 优化**：
- 同样使用计数器替代完整内存扫描
- 减少 GC 检查频率

- 添加 `src/lr_compress.c` 到编译列表

## 测试结果

### 字节码缓存 + 压缩
```

./lr_js --bytecode-cache /tmp/cache script.js

→ 缓存文件: c4c0e72119bceab4.lrfile (199 bytes)

# 第二次运行（缓存命中，自动解压）
./lr_js --bytecode-cache /tmp/cache script.js
→ Hits: 1, Hit rate: 100.0%
```

### 日志级别动态调整
```c
// 默认 INFO 级别 - DEBUG 消息被过滤
lr_slog_debug(sb->log, 1, "This won't be logged");

// 运行时切换到 DEBUG
lr_sandbox_log_set_level(sb->log, LR_SLOG_DEBUG);

// 现在 DEBUG 消息会被记录
lr_slog_debug(sb->log, 2, "This will be logged now");

// 查询当前级别
LR_SandboxLogLevel lvl = lr_sandbox_log_get_level(sb->log);
// 用于线上问题排查：远程调用切换为 DEBUG，排查完切回 INFO
```

### 性能优化对比
- **eval 热路径**: 移除每次 2 次完整堆扫描 → 仅计数器递增
- **GC 检查**: 从每次 eval → 仅当计数器超阈值时
- **启动速度**: 无变化（初始化代码未改动）

## 关键设计决策

1. **LZ4 而非 zstd**: 选择 LZ4 因为：
   - 纯 C 实现约 200 行，无外部依赖
   - 解压极快（~2-4 GB/s），对加载性能影响极小
   - 压缩率 40-60% 对 JS 字节码足够

2. **智能压缩**: 仅当压缩节省 > 10% 空间时才启用，避免小数据膨胀

3. **动态日志级别**: 线程安全的 `current_level` 字段，`write()` 时检查过滤器

4. **性能优化策略**: 用简单计数器替代完整内存扫描，减少 eval 开销
